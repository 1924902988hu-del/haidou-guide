# 抖音视频资料层

海斗速查采用两段式流程，而不是在“视觉模型”与“爬虫”之间二选一：

1. 采集层使用 TikHub 关键词搜索拿到公开链接、标题、作者与发布日期。采集失败必须保留失败状态，不能生成摘要。
2. 理解层先用 FFmpeg 做 3 秒粗抽帧与结尾 0.5 秒密集抽帧，再用 macOS Vision OCR 定位装备、强化、符文和加点界面；命中关键界面或当前标准名后，对前后 4 秒按 0.5 秒补帧。BiliNote 仍必须启用 `video_understanding`，同时核对画面、字幕与语音，再输出英雄、核心强化、装备方向、关键操作与版本风险。
3. 发布层只读取 `data/videos/catalog.json`。只有 `multimodal-reviewed`、`visual-reviewed` 或 `human-verified` 才能显示“已看画面”；仅有页面元数据的内容必须标为 `metadata-only`。

站点不托管抖音原视频，只展示带来源链接的结构化摘要。每条记录包含 `publishedAt`、`reviewedAt` 和 `patchStatus`；公开视频版本状态对照的是站点的“客户端资料快照”。OP.GG 攻略与 hexdata 统计各自保留独立版本，避免上游不同步时把混合来源误写成同一补丁。

公开网页与发现阶段共用 45 天近期窗口。每条通过记录写入 `expiresAt`；到期后记录仍留在视频目录供审计，但站点构建会自动隐藏它并让该英雄回退到原有 OP.GG 内容。每次静态数据更新后，构建还会重新检查视频中的强化、装备、符文和召唤师技能；任何名称已被删除或不再适用于海克斯大乱斗时，同样自动隐藏并回退 OP.GG。年龄只能证明“不再满足近期口径”，不能单独证明视频结论已被游戏机制证伪，因此不会仅凭日期把记录标成 `obsolete`。

## 当前实现

`pipeline/video_intelligence.py` 提供四个命令：

- `discover`：搜索候选视频并按英雄匹配、发布时间与互动量排序。
- `analyze`：提交单条视频给本地 BiliNote，保留原始笔记并生成结构化草稿。
- `publish`：只允许通过质量闸门的草稿进入视频目录，然后重建并验证全部英雄页。
- `refresh`：把前三步串成一次批量刷新；默认只产出草稿，加 `--publish` 才会更新网站。

默认质量闸门：

- 英雄 alias 必须与搜索目标一致；
- 候选必须在 45 天内、时长不超过 10 分钟，并同时命中英雄、海克斯大乱斗模式和攻略意图；整活/集锦标题会被排除；
- 至少提取一种可逐项验证的强化、出装、符文、加点或召唤师技能；只有打法概述不能发布；
- 至少两条有效时间戳证据；
- 每条证据时间戳必须严格早于候选视频的 `durationSeconds`；指向视频结束或之后的时间点不能作为证据；
- 至少一条时间戳证据必须明确出现目标英雄的官方中文名或 Data Dragon alias；标题、搜索词与模型填写的 `hero` 字段不能替代英雄身份依据；
- 至少一条证据必须来自实际画面；
- 模型自评置信度不得低于内部闸门 0.68；该值尚未用本项目样本校准为正确率，只参与候选筛选；
- 只有视频明确提到并等于站点客户端资料快照补丁时，内部状态才能标为 `current`；公开徽标显示“视频提及 26.xx”，不宣称这是浏览时的实时当前版本；
- 当前装备、强化和符文名称必须存在于本地词典；仅供竞技场等其他模式使用的装备、已删除符文、歧义俗称和 OCR 猜词会被拒绝；
- 每件结构化出装都必须按标准全名出现在装备语境的时间戳证据中；同名强化不能替代装备证据；
- 每项结构化强化与符文都必须按标准全名出现在时间戳证据中；同类泛称和结尾总结不能代替逐项覆盖；
- 单条视频最多保留四套有独立证据的流派；每套必须有唯一 `id` / `label`，具体搭配证据必须写入相同 `strategyId`。装备顺序只要求在各自流派内唯一，不能跨流派借用证据或摊平成一条列表；
- 展示技能加点时，至少一条时间戳证据必须明确说明加点，并覆盖结构化字段中的 Q/W/E/R；
- 无蓝英雄不能采用依赖法力的装备；召唤师技能必须在当前 Data Dragon 的 `ARAM` / `KIWI` 模式中可用；未经证据支持的“当前版本”与夸张外部效果声明会被拒绝。

分析提示会注入本地 `hexdata` 中有模式统计的强化名称，并合并当前 CommunityDragon 客户端 `UX/Kiwi` 目录中的海克斯大乱斗标准名称；后者只用于确认名称合法，不代表已有统计或当前推荐。装备名称仅接受当前 Data Dragon 标记为嚎哭深渊（地图 12）可购买的条目，或在当前 `hexdata` 海克斯大乱斗样本里真实出现的模式专属条目；“在任意地图可用”不足以证明适用于海克斯大乱斗。召唤师技能只允许 Data Dragon 标记为 `ARAM`、`KIWI` 或 `KIWI_JADE` 的当前名称。模型无法唯一匹配时必须留空，不能用俗称或 OCR 猜测补全。结构化结果只允许经过代码中 `SAFE_NAME_ALIASES` 审核的一对一别名自动标准化，并在草稿的 `normalizations` 字段保留变更记录；“瞄准镜”“轻语”等可能对应多个合法条目的名称仍会被质量闸门拒绝。

补丁状态也必须由证据约束：只有证据文本在同一时间戳明确出现当前补丁号时，记录才能标为 `current`。标题、发布日期或模型推断都不能替代视频内证据。

`data/videos/patch_impacts.json` 只收录官方补丁公告能直接证明、且发生在视频发布后的英雄或机制调整。命中时，记录继续保留视频原始搭配证据，但追加官方来源、发布日期和具体影响；这不会把视频自动升级为当前答案，也不会仅凭一次数值调整删除仍可核对的搭配。当前 26.15 对千珏伤害修正和索拉卡治疗修正的改动属于此类直接影响。

多模态草稿保留模型生成的原始标题、摘要、理由、打法与置信度，便于后续人工复核；自动发布到网页时按流派分别投影当前词典合法、且通过该流派逐项时间戳证据闸门的搭配名称，并生成确定性摘要。同一视频中只要仍有至少一个搭配名称通过闸门，就可以发布这个证据子集；其余识别结果及省略原因只留在内部草稿的 `projectionOmissions`，不会以完整攻略的口吻公开。公开证据同步重写为只包含目标英雄与已保留搭配，模型生成的原始效果、理由、打法、适用条件和推测性 caveat 均不进入这类子集记录。英雄身份、时效、画面证据、版本和置信度等其他闸门保持不变；若没有任何搭配通过，英雄页继续使用 OP.GG。模型自评置信度也会在构建时从公开站点 JSON 中移除，网页不展示未经本项目真实样本校准的百分比。

`multimodal-reviewed` 表示 BiliNote 使用了关键帧与语音转写进行提炼，不表示每条公开结论同时拥有画面、字幕和语音三类依据。网页的 `analysisLabel` 由正式记录中的 `evidence.kind` 自动生成，例如“AI 提炼 · 证据：画面、字幕”；验证器会拒绝标签与公开证据类型不一致的记录。

分析阶段会读取 BiliNote 同一任务的原始 `_markdown.md`，按上游实际替换顺序把 `Screenshot-[mm:ss]` 标记与最终 Markdown 图片一一绑定；截图复制到已忽略的 `data/cache/video_intelligence/frames/`，草稿保存相对路径、时间戳、原始/处理后 Markdown 哈希和图片 SHA-256。标记与图片数量不一致、源文件缺失或路径不安全时按不可用处理。公开 `kind=frame` 证据只有在清单中存在同时间戳截图时才能通过质量闸门。这个清单证明“哪张图来自哪个抽帧时间”及文件未被替换，不等于自动证明图片语义；人工认证仍需实际看像素。

`pipeline/frame_intelligence.py` 的 OCR 与感知哈希图标匹配首先生成定位候选，不能单独把新搭配写入公开记录。提示上下文会从完整视频时间线均匀取样，避免长视频只把开头关键帧交给模型；图标匹配采用低误报阈值，未达到阈值宁可不返回。模型完成后还有第二道本地交叉闸门：每个结构化强化、装备和符文必须在其 `kind=frame` 证据时间点前后 3 秒内再次被 Vision OCR 命中，否则整条视频不自动发布并回退 OP.GG。英雄身份若在本地 OCR 读到官方名、alias 或项目已登记俗称，可补成带 `source=local-vision-ocr` 的时间戳证据，但不会据此补写攻略搭配。可用 `python3 pipeline/frame_intelligence.py audit-cache --max-videos 20` 对已有截图做离线金标预检，这个命令不会调用 TikHub 或模型。

`--all-heroes --resume` 会按英雄写入候选断点和多模态草稿。恢复运行时不会直接信任旧质量结果，而是按当前词典、别名表、关键帧 OCR 和质量规则重新判定。已有候选断点进入分析阶段时应加 `--skip-discovery`；该模式要求显式提供 `--candidates-output`，并保证 TikHub 搜索新增为 0，只保留逐条媒体详情解析和 BiliNote 分析。若断点已覆盖全部目标英雄，普通恢复的发现阶段也不会初始化 TikHub 客户端。`--max-search-requests` 只约束本轮新增搜索；候选断点的 `lastRun` 会分别记录 `searchRequestsAdded` 与 `checkpointSearchRequestsTotal`，批次摘要另记新分析次数和缓存重判次数，避免把历史累计误报成本轮费用。价格字段只采用 [TikHub 当前公开区间](https://tikhub.io/pricing) 的上限做本轮搜索估算，不包括媒体详情解析和本地 BiliNote，且不能代替真实账单。全量发布只替换视频资料层：通过的记录加入 `data/videos/catalog.json`，没有候选、分析被拒绝或基础设施失败的英雄继续显示原有 OP.GG 攻略。

TikHub 的签名播放地址、抖音 Cookie、BiliNote 临时视频和模型密钥不会写入仓库。缓存草稿与截图证据位于已忽略的 `data/cache/video_intelligence/`；它们用于本地审计，不会被公开站点托管。

## 录入字段

- `heroes`: Data Dragon alias，例如 `Blitzcrank`
- `analysisStatus`: `metadata-only`、`multimodal-reviewed`、`visual-reviewed` 或 `human-verified`
- `patchStatus`: `current`、`needs-game-check` 或 `obsolete`
- `summary` / `keyPoints`: 只写画面、字幕或语音能够支持的内容
- `strategies`: 同一视频内彼此独立的流派数组；每套包含唯一 `id`、`label`、强化、装备、符文、技能、召唤师技能与打法
- `strategy`: 首个流派的向后兼容投影；新代码应优先读取 `strategies`
- `evidence`: 时间戳、证据类型（`frame` / `subtitle` / `audio`）、多流派时的 `strategyId` 与对应结论
- `expiresAt`: 公开网页近期窗口的最后有效日期；过期记录不进入英雄页
- `confidence`: 0 到 1 的模型自评，仅保留在内部目录用于质量闸门；未校准为正确率，不进入公开站点 JSON，也不代表套路胜率或人工认证
- `caveat`: 版本、样本或机制风险

带登录态的本地采集可以使用浏览器 Cookie，但 Cookie、临时视频和签名媒体地址不得写入仓库。GitHub Actions 只发布已经审核过的结构化记录。
